## Notes on this matrix

- "Computed" topic0 values were derived via `keccak256(signature_string)` and cross-checked
  against the one value already deployed in production code
  (`TRANSFER_TOPIC0` in `scanner.ts`, `0xddf252ad…`) — the computation method matched exactly, so
  the same method is trusted for the other signatures, though those specific values have not
  been independently confirmed by observing a real matching log on-chain (no CCTP burn, mint, or
  P2P escrow event currently exists in `chain_events`, since none of those are decoded yet).
- Every "No" in the Indexer Detects column for CCTP/UB/P2P is **consistent with the codebase's
  own stated design intent**, not an oversight discovered by this audit — `blockchain-indexer`'s
  and `activity-consumer`'s own header comments both explicitly scope the indexer to being a
  generic Transfer-log/native-value observer, deliberately not a per-feature decoder.
- The one **new, real gap** this matrix originally surfaced beyond what was already known:
  BulkPay/Multicall3 transfers are *incidentally* visible to the indexer (via the generic
  Transfer scan) even though nothing decodes them as BulkPay specifically — which is exactly the
  scenario the `chain_events` dedup fix was written to protect against. That gap is now **closed
  at the schema level** — see `docs/PHASE_3_FIXES_APPLIED.md` for the applied migration and its
  verification (including a real before/after reproduction of the exact multi-recipient
  collision this matrix flagged).
